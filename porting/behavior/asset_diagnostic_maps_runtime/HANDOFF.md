# FFortAssets diagnostic maps: key and read behavior recovered; mutations unresolved

Image `/mnt/vibrato/fortnite-evidence/original-late-capture-1/image-125.runtime.bin`, base 0x140000000, SHA-256 338c83a2314ccac1040a2c0bb520b893013cc7b58eda58e550da67f5d84de680. No tests or build were run. This is a bounded read-side proposal, not a complete implementation of the two maps.

The previous handoff's interpretation of the 24-byte copied element as an 8-byte key and FString value is wrong. The copied object is an entire `FSoftObjectPath`: its `FName AssetPathName` at +0 and `FString SubPathString` at +8. The sparse element at stride 0x28 consists of this path at +0, a 32-bit count at +0x18, padding, and set hash metadata at +0x20/+0x24. A `TMap<FSoftObjectPath, int32>` matches the observed fields, but the actual insertion, equality, hashing, and mutation semantics have not been traced, so a production declaration is not yet justified.

* 0x141def82f and 0x141defa2f iterate +0x10 and +0x60 respectively and pass each element start to 0x142eda0f0. That function converts the FName using 0x142ce9f90, appending `:` and the FString at +8 if present. This matches `FSoftObjectPath::ToString` and the local engine declaration `/opt/fortnite/UnrealEngine/Engine/Source/Runtime/CoreUObject/Public/UObject/SoftObjectPath.h`. The diagnostic passes element+0x18 separately to 0x140a86a60, which reads precisely its first dword at 0x140a86b66; it puts that in a temporary FString/int32 map. The temporary is logged at 0x141defc54 using `  %s (%d)`. Thus the count's signed 32-bit interpretation is supported by the consumer; no meaning or update policy for it is established.
* 0x141df6860 appends copies of keys from +0x10 followed by +0x60 to an existing `TArray<FSoftObjectPath>`, preserving sparse iteration order and duplicates between maps; 0x141dfb390 appends keys from +0x10 only. Both compare array capacity to the number of entries (combined for the first), reserve if needed, and deep-copy the FString via 0x140682ce0. They do not append the count, clear the destination, or lock the owner. See `ReadSide.proposal.cpp`.
* 0x141de4b00 initializes both collection headers empty. 0x141de77f0 tears them down in reverse order via the same helper 0x141982a40, after removing delegates; separate backing allocations and hash storage are freed. No evidence that keys or their strings are GC references. The teardown fits owning keys with normal FString destruction.
* The local engine's `GetTypeHash(FSoftObjectPath)` combines FName and FString hashes, but this is not proof that original map insertion used that key policy. Do not assume unique-key replacement, increment-on-insert, zero removal, or a lock. We found no insertion or removal call. A direct-call scan of singleton 0x141df61e0, tracking its returned RAX until overwritten or the next call, found member +0x10 only at 0x141def698, 0x141df68cc, 0x141dfb3eb; all are readers. A raw RIP-displacement scan of the first 0x6000000 bytes of the image for exact static bases +0x10 and +0x60 found only +0x60 reads at 0x141def9c2 and 0x141df6b8a. These are bounded scans, not proof that writes cannot use other owner aliases, wider offsets, or different addressing. Constructor, destructor and callbacks receive owner directly, and must also be considered. Continue from direct-this accesses and xrefs to the map helper 0x141982a40 before declaring mutation behavior or shipping layout.
