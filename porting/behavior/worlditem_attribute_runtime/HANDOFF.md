# World item attribute conversion

`DeserializeAttributes.h` is a proposed callable implementation of 0x1410f59b0, not wired into canonical code or compile-tested. It requires JsonUtilities. The original uses a fresh FJsonObject, inserts each attribute's FString and shared JSON value, then calls 0x143eecfa0 with its Values map, the supplied UStruct, output address and both flags zero. 0x143eecfa0 forwards directly to 0x143eecfd0 with the struct and output also passed as the enclosing container; this matches the local engine's public `FJsonObjectConverter::JsonAttributesToUStruct` implementation. The diagnostic in 0x143eecfd0 says `JsonObjectToUStruct`, but the directly corresponding public entry point is JsonAttributesToUStruct. Existing engine version and source/binary equivalence are not independently established beyond this matching control flow. Use the engine implementation rather than a hand-written field subset, so its conversion, errors and return value remain available. The converter writes directly into the destination: failure can leave earlier fields changed, and must not be rolled back. Missing keys are skipped; this is not a completeness validator.

`WorldItemAttributes.h` proposes callable equivalents for 0x141df62a0, 0x141df6530 and 0x142035080; these are not integrated or compile-tested. 0x142035080 calls the helper with FFortItemEntry::StaticStruct and returns false immediately if it fails, without clearing AlterationInstances. On success it sets AlterationInstances.Num to zero, grows capacity if needed for AlterationDefinitions.Num, then visits each definition string in order. It asks the Fort asset manager for the asset, accepting it only if castable to UFortAlterationItemDefinition, appends successes, and logs `Failed to find asset for alteration %s` for missing or wrong-class results; either failure continues and the function ultimately returns true. Duplicates are retained. The lookup helper 0x141df6530 splits the input on `:` to build a primary asset ID, asks manager vtable +0x2a0 for an already available object, then +0x2b0 for its path and resolves/loads it via 0x142eda260 if necessary. 0x141df62a0 performs a global manager class check and includes an error path; don't replace this with a simple map lookup or silently change its diagnostics. The manager constructor 0x141de5fc0 installs vtable 0x145fdd7d0. Its +0x2a0 entry 0x14401e000 gets the primary asset record and its weak object, matching UAssetManager::GetPrimaryAssetObject; +0x2b0 entry 0x14401e3f0 gets the same record and copies its soft path, matching GetPrimaryAssetPath. The path helper 0x142eda260 matches FSoftObjectPath::TryLoad including top-level loading, subobject resolve, StaticLoadObject and redirector traversal. Both diagnostics use category global 0x1481348e0, identified as LogFort in aircraft_lookup_evidence.md; severity 1 is Fatal for the invalid manager and 3 is Warning for the alteration. The lookup helper uses FString::Split at the first colon and creates FNames only on success, so the proposal preserves that instead of substituting a potentially different parser.
