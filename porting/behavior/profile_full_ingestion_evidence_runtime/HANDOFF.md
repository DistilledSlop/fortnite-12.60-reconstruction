`0x141106ef0` and `0x1421f3d30` call `0x14110e120` during setup/reset; neither caller itself ingests the response. The full-update loader `0x1410ffa80` uses the profile's existing backing at +0xd8 and reconciles it; replacing the backing for every full response would discard identities and is not supported by this evidence.

`0x141102520` copies the update's lock expiration to profile +0xd0 and handles release of a previously held lock when expiration becomes zero. It constructs an update context, recording profile, incoming command revision, and previous backing command revision; calls `0x1411028a0`; dispatches backing virtual +0x68 with `(status != 4, context)`; then calls `0x1410f4310(profile, context)`. The exact context's notification semantics and both post-update bodies need closure. Do not equate the reflected `Notifications` array with these callbacks without tracing its consumption.

`0x1411028a0` writes incoming `ProfileCommandRevision` to backing +0xf8 even if the response profile revision equals current profile +0xc0; in that equal case it immediately returns status 0, before scanning changes. Otherwise it stores a timestamp and incoming `ProfileRevision` at profile +0xe0 and +0xc0 before inspecting changes. A negative `ProfileChangesBaseRevision` falls back to incoming revision minus one. An empty change array returns 0 after those writes. It scans the changes for the full-update discriminator before processing deltas; a matching change obtains its profile object and invokes `0x1410ffa80`, immediately returning status 2 or 3 depending on whether the old profile revision was nonnegative or negative. Missing profile or failed full loader returns 4; no rollback of the earlier revision write is visible. Verify discriminator literals and call arguments in the original image when integrating. Delta handling compares old revision with base (with an additional context flag permitting old <= base), applies changes in order on the matching path, and otherwise invalidates revision and initiates recovery. Its error and logging branches require assembly review before claiming a complete state machine.

The full loader first extracts nested profile stats and calls `0x141107e00(backing, context, ...)`. It collects existing IDs whose item +0x90 is nonnegative into a temporary set, then iterates the response item object. An existing ID is removed from this set. For a new ID it constructs a shared item with that ID, calls `0x1411042a0`, adds it to the ID map and both group indexes, and calls `0x141104e20` on the context. Existing entries are compared by template ID using the recovered folded comparison. On template change it calls `0x141104f40`, refreshes the existing shared entry with `0x1411042a0`, and conditionally calls the object bridge when backing +0x178 is set. For unchanged template it compares/updates attributes and quantity, including item-aware object calls. After iteration, remaining eligible IDs are looked up, passed to `0x141105070`, and removed via `0x14110bed0`. Entries with negative +0x90 are not added to that removal candidate set. Exact field keys, side-effect ordering within helper bodies, group reindexing on changed template, failure return and stats semantics remain to be established. The existing item's shared identity is retained on the update branches shown.

The base ID and grouping maps own non-thread-safe shared references, while the item +0x88 UObject needs reporting by the profile owner collector together with registry class references; see `../profile_backend_mutation_runtime/HANDOFF.md`, `../profile_entry_lifecycle_runtime/HANDOFF.md`, and `../profile_registry_support_runtime/HANDOFF.md`. The per-item weak profile reference and class/object bridge do not replace this collector. Existing entry JSON and notification proposals document narrower recovered operations, not a complete transaction.

No implementation is proposed here: unresolved removal, group reindexing, stats, context callbacks, error behavior and collector integration make a partial live loader unsafe. No build, runtime execution, tests, canonical edits, or commits were performed.
