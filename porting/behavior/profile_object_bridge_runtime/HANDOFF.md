# Profile object bridge

Proposed integration fragments are `BridgeIntegration.h` and `BridgeIntegration.cpp`; these are not compiled standalone files. Apply declarations to the generated profile and interface through the owning generation mechanism. The names `ItemClassRegistry`, `CreateItemObject`, `UpdateItemObject` and `McpItem` are assigned names, not recovered symbols. `PopulateFromMcpItem` is supported by the native failure diagnostic. The implementation omits that diagnostic on population failure; object state and dispatch are otherwise represented. The exact const/reference spelling and whether the interface method has a base implementation need compiler/UHT integration review; `= 0` in the fragment is a proposal and not proven by the call site. In particular check the generated interface virtual layout: the call is at interface vtable +0x10, and the engine-generated `_getUObject` is a candidate for the intervening slot +8. Do not add a second artificial virtual slot without checking the target engine's macros.

It is a virtual call; retain overrides in derived classes.

The registry begins at profile +0x30. Lookup 0x140b77eb0 walks 0x20-byte map elements with FString at +0 and UClass pointer at +0x10, hashes UTF-16 text via 0x140682990, and compares with 0x142bcf780: ASCII characters are case folded and non-ASCII code units compared directly. The ordinary target UE FString key implementation should be checked against this behavior. Bridge first looks up template ID then alternate key when the first value is absent or null. Both absent/null clears the existing object. With the same exact class and force false, it returns without touching the interface. Otherwise it creates through the virtual only when the existing pointer is null or has a different exact class. Failed creation leaves null; missing interface retains the created/existing object; failed populate clears the pointer; successful populate retains it. It assigns the weak owner profile before any lookup.

Bridge receives an owning shared pointer pair by value and releases its non-atomic strong count on every exit. The item-aware subobject has pointer at +8 and control block at +0x10; assignment increments the new block's non-atomic weak count at +0xc before decrementing the old one. Strong count is +8 and object destruction occurs when it reaches zero, followed by weak count release. This is a non-thread-safe TWeakPtr to the shared entry, not a weak UObject. Populate receives the raw entry pointer. Null input is not checked. When integrating collection, the profile must report live item object pointers, and registry UClass pointers require the same lifetime/GC treatment as the original; see profile_entry_lifecycle_runtime/HANDOFF.md.
