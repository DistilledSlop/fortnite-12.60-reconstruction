# FFortAssets +0x150 collection proposal

Superseded integration status: see ../asset_owner_materialization_runtime/HANDOFF.md and source batch40 in ../../HANDOFF.md. Earlier blockers below are historical evidence; diagnostic map writers and changed-mode caller wiring remain open.

Image 125, base 0x140000000, SHA-256 338c83a2314ccac1040a2c0bb520b893013cc7b58eda58e550da67f5d84de680. This is a bounded proposal, not a complete FFortAssets implementation and not yet integration-ready: the enclosing owner lifecycle and complete consumer inventory remain unresolved.

* 0x141de9f00 rejects null first input, then obtains the singleton and passes the address of its first input and the second input as a pair of addresses to 0x141de4030. No owner lock is taken there. The latter copies the two eight-byte values into offsets 0 and 8 of a 24-byte set element; offsets 0x10 and 0x14 are hash chain and bucket metadata. The key is pointer-hashed (pointer shifted right four and mixed).
* 0x140991960 follows a bucket chain, compares only the first eight bytes, copies 16 bytes over the existing element on equal key, and discards the newly allocated element. Thus this is unique-key map Add/replace, not a multimap or a plain set.
* 0x141de3560 iterates allocated sparse elements at stride 24 and calls FReferenceCollector virtual +0x38 exactly once per element, passing the address of offset 0 and its two caller-supplied contexts. 0x141de9e80 supplies null contexts and invokes this after releasing the owner lock. The equivalent UE FReferenceCollector::AddReferencedObjects(TMapBase<KeyType*, ValueType,...>&) overload in local UnrealEngine/Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectGlobals.h visits keys only. Its pointer-key/pointer-value overload visits both, disproving an unqualified UObject pointer value interpretation. The payload is not passed as a GC reference here.
* 0x140992250 clears sparse storage and hash with caller slack; the observed caller passes zero. `Entries.Empty(0)` expresses the same container operation. The owner's clear occurs while locked, but GC and insertion do not take that lock; this helper does not invent synchronization.
* The payload is FName. Callers 0x14251dad0 and 0x14251dcd0 copy `this+0x18` before resolving soft references; their diagnostic text identifies CommanderPerk fields. This is the UObject name field: local UE `UObjectBase.h` has flags and index, class pointer, then `FName NamePrivate`, at +0x18 on 64-bit. Other callers 0x141d52490, 0x14237bc20, and 0x1424bac90 likewise copy that field. The diagnostic at 0x141deff92 walks +0x150 and passes value address +8 to 0x142ce9f90, also used on key UObject+0x18; the converter decodes a 32-bit name index and 32-bit number and produces text. These independent field and consumption paths support `TMap<UObject*, FName>`.
* Direct byte-scan of image for 0x141df61e0 relative calls found 260 sites; disassembling the subsequent 110 bytes found +0x150 at insertion 0x141de9f12, clear 0x141ded274, and diagnostic traversal 0x141deff92. This bounded scan is not proof against more distant accesses or aliases; GC, constructor and destructor are separately known owner methods. Ghidra reports 16 direct insertion calls from 14 functions, and one data reference to the wrapper. Diagnostic traversal needs preserving by the eventual owner; this collection helper intentionally exposes Entries for that purpose.

No tests or build run. Original owner constructor/destructor, registration callbacks, clear trigger, diagnostic behavior and any accesses beyond the bounded inventory must be independently closed before integration. No claim is made that this proposal completes the shared tracker.
