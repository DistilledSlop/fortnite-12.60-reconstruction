# Quest condition lexical consumers

The two custom consumers and matching helpers were captured in ignored `porting/generated/quest-token-callbacks`, `quest-lex-helpers`, `quest-lex-helpers2`, and `quest-lex-helpers3`. These are static decompilation findings, not runtime tests.

* Consumer 20 (`0x14240db90`) initializes a double to zero and calls `0x142c59330` on the stream; on a nonempty parsed span it emits a node of GUID type `0x142419c70` carrying the double. `0x142c59330` fetches static format rules from `0x142bf1ab0`, calls `0x142c59390`, and the latter invokes the number parser `0x142c02ec0` and makes a token only when its parsed length is positive. This matches the UE `ParseNumber` / `FastDecimalFormat` pattern; static format setup includes ASCII `NaN`, `-`, `+`, comma and period. Complete numeric edge cases and exact equivalence to UE culture-agnostic no-grouping rules remain to be checked against `0x142c02ec0` and the native parsing-options object (`0x142c1e750`); do not replace it with an assumed numeric grammar.
* Consumer 21 (`0x14240d980`) consumes a nonempty maximal run for which `0x14240a540` returns Continue: the C wide-character `iswalnum` predicate succeeds or the character is `.`, `:` or `_`. There is no first-character restriction in that predicate. It copies the run, constructs an `FName` using the native name constructor with its second argument 1, and emits the same `0x142419c70` node type with a discriminator and that name. A nonmatching first character produces no token. Exact platform/locale behavior of native `iswalnum`, FName creation mode and the operand node's full variant semantics require further review.
* The 21 registered consumers are tried in order, so the numeric consumer precedes the name consumer. A successful number prefix can therefore take precedence over an otherwise permitted name run; exact numeric prefix length must follow the native number parser. The constructor enables ignored whitespace at token definitions +0x50; UE's ordered token loop skips it before trying definitions.
* Symbol and keyword callbacks use `0x142ca3680`, which matches the literal at the current position without checking an identifier boundary. Its comparator `0x142bcf940` folds ASCII through a 128-byte lookup table (`A`–`Z` map to `a`–`z`); characters outside ASCII compare by their raw UTF-16 value when different. Consequently keyword matches are ASCII case-insensitive and can match prefixes, subject to earlier consumer order. This differs from the case-sensitive `FTokenStream::ParseToken` overload in the checked UE source and must be preserved explicitly. The same native matcher tests aliases `and`, `or`, `not` and `HasTag`.
* The apparent alternate symbol lookup in callbacks for parentheses, `+`, `-`, `*`, `/`, `%`, and `^` calls `0x1423f8930`. Its entire native body returns null, so those paths have no alternative string in this build. The explicit aliases listed above are real; they are tested if their primary symbol did not match.

The shared operand GUID does not prove all evaluator or tag-reference behavior. The singleton's grammar/operator handlers, the exact numeric parser and Unicode character handling remain blockers. Probe transactions were rolled back; Ghidra nevertheless reported project metadata changes on opening. No generated source, build or runtime tests were performed.
