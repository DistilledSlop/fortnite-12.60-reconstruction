# Quest condition evaluation and tag extraction

The singleton has multiple operator jump tables. The constructor registers one group on the table at +0x1a8, another at +0x2e8, and a further group at +0x428. In particular, it registers `0x1423f91e0` (`HasTag`) and `0x1423f9690` (`MissingTag`) on +0x1a8, but `0x1423f90f0` and `0x1423f95a0` on +0x428. These share operand type GUID getter `0x142419c70` but route to different handlers. The +0x428 table also registers comparison/equality handlers and `&&` / `||` for GUID type `0x1424196f0`; it does not simply reuse boolean evaluation. Native helper captures are in ignored `porting/generated/quest-eval-probe`, `quest-eval-handlers`, `quest-eval-impl`, and `quest-eval-extra`.

`0x142414d50`, used by the row validation path, evaluates the compiled token array using `0x142c92890` with the +0x428 table. The latter has the UE expression-evaluation structure and invalid-expression diagnostics. Extraction proceeds only on a successful value of GUID type `0x1424196f0` and a non-null payload; it iterates a 24-byte-stride array in that result and appends entries whose non-null label contains `Tag` (native string search `0x142bace90`, flags 0/0). It copies the entire 24-byte entry. It does not lexically scan every identifier or return every name. The row validation caller then requests the gameplay tag represented by each appended entry with missing-tag error reporting disabled; invalid requests cause validation to fail. Mixed-operator and parse/evaluation failures can therefore suppress tag output and must not be replaced by a direct scan.

For the +0x428 table, the `HasTag` registration wrapper `0x14240a420` routes to `0x1423fff70`; `MissingTag` wrapper `0x14240a6b0` routes to `0x142402ac0`. Each tests the operand variants and, when either is an identifier (discriminator 1), constructs an entry using the right operand's FName and the respective literal label `HasTag` or `MissingTag`; otherwise it returns the native shared default result. Preserve exact variant and error semantics before lifting. The contextual +0x1a8 handlers `0x142404c40` and `0x142401000` instead require both arguments to be identifiers and have distinct localized errors; they are not interchangeable with extraction handlers.

The +0x428 `&&` handler is `0x142401f70`; `||` is `0x142400d10`. Both combine result structures and explicitly return a localized `MixtureOfAndsAndOrsNotSupported` error if a combined expression mixes those operator kinds. Comparison helpers include `0x142403950` (`<`), `0x1424046b0` (`<=`), `0x1424002d0` (`>`), `0x142401b30` (`>=`), `0x142404070` (`==`), and `0x1424025e0` (`!=`). They construct nontrivial condition structures, not plain bools. Arithmetic uses a separate table and operand variant: division `0x142400ba0` returns discriminator 2 and logs on division by zero or nonnumeric operands; unary minus `0x1424009f0` has an explicit nonnumeric error path. Generic helper `0x14240ff60` checks both numeric discriminators and conditionally logs type errors.

Additional result-structure constructors, merge helpers, operand conversion and all evaluator node/lifetime semantics remain unresolved. Captured native wrappers do not justify declaring an executable evaluator complete. No implementation, manifest change, build or runtime test was made. Ghidra probe transactions were rolled back, though Ghidra reported project metadata changes on open.
