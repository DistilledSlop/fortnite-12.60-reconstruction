# Client-event dispatcher evidence

The original client's `UFortKismetLibrary::ExecuteClientEvent` thunk at `0x14296a4b0` calls `0x141eece20`. That body resolves a world and casts its game instance via `0x141e5b2c0`, then calls dispatcher `0x141e59c80` or logs `No WorldContext!`. The class accessor `0x1428ea7f0` identifies the cast as `UFortGameInstance`; `0x142877b10` identifies the dispatcher interface check as `UFortClientEventInterface`.

The dispatcher constructs `HandleClientEvent_%s` from the `EventName` field of the supplied event type and also queries a fallback handler. The fallback FName global `0x148137770` is initialized by `0x1402d5910`: it constructs an FName from the UTF-16 string `Undefined` and stores it in that global. Thus the fallback handler is `HandleClientEvent_Undefined`. The Ghidra references to the global are the initializer, two reads in dispatcher `0x141e59c80`, and a read in thunk `0x142ad6d70` used in an argument default. These observations do not establish all dispatch argument semantics.

The listener registry is native state at `UFortGameInstance + 0x6c0` in this original binary. Lookup `0x141e62a90` finds entries by handler name, adds valid weak-object targets to the output collection, and removes invalid weak pointers. `0x141e60900`, identified by its `STAT_Fort_FortGameInstanceGetGlobalEventsForObject` string, inspects objects implementing `FortClientEventInterface` and collects UFunction names starting `HandleClientEvent_`. `0x141e78cb0` adds the object under these names, while `0x141e84a70` is the paired removal path. An original post-load-map path `0x141e72150` also invokes registration.

Frontend paths `0x144e0f0a0` and `0x144e0f3e0` invoke registration and removal respectively, after `0x144dba3f0` obtains the object's world and casts its game instance. The exact owner class and lifecycle methods remain unresolved. The original runtime dump has both paths in adjacent slots `+0x318` and `+0x320` of a vtable starting at `0x146d14438`; other vtables also contain the pair or override them. A vtable occurrence alone does not identify its class or lifecycle semantics. The generated class lacks this non-reflected registry, and no implementation has been ported.

Reproducible raw outputs, ignored by git, are under `porting/generated/frontend-native-evidence/`: `ui-helper-candidates/`, `ui-helper-bodies/`, `execute-client-event-deps/`, `event-registry/`, `event-registration/`, `event-registration-callers/`, `event-registration-lifecycle/`, `fallback-owner/`, `fallback-xrefs.txt`, and `owner-vtable-xrefs.txt`. The function directories were produced with `porting/ghidra/probe_callees.py` using their adjacent input JSON files; the two xref files came from read-only PyGhidra reference queries. Ghidra's program edits were rolled back for the function probes. These are binary-analysis results, not a runtime test of frontend behavior.
