This source evidence map recovers the original legacy Panel activation queue:
record layout, public argument routing, enqueue cleanup, every queue branch,
five weak completion callbacks, reset and delayed input resumption. The native
implementation is not applied. The selected live UI-manager policy, complete
held-action dispatch and nonlegacy bindings remain integration dependencies.
No runtime or complete-manager compatibility is claimed.

## Public contracts and enqueue

Public PushActivatablePanel exec `1408107e0` reads arguments in declaration order
Panel, bIntroPanel, bOutroPanelBelow, then calls `1407e55a0`. That wrapper sets
the internal fourth argument **bActivatePanel=true**, forwards the caller's
bOutroPanelBelow as the fifth argument, and calls InternalPushActivatablePanel
`1407ce8a0(manager,panel,bIntroPanel,true,bOutroPanelBelow)`.

InternalPush first computes a **predicted stack** via `1407ad3f0`: copy the
current stack, then walk queued records in order; Push appends its Panel; Pop
finds the first matching Panel and removes that element and every element above
it. Intro/Outro have no effect on this prediction. The old current-stack
membership check only feeds a mismatch diagnostic; acceptance uses the predicted
stack. Null Panel or Panel already predicted on stack yields no enqueue.

For an accepted push, if predicted stack is nonempty, generate an independent
GUID and submit an Outro with **null Panel** through AddCleanOp `1407a95e0`.
Then generate a second GUID and append Push with the actual Panel directly to
Operations. Both carry the three internal flags. If manager byte `e0` is false,
call BeginOperationProcessing `1407ab920`. The direct Push append is distinct
from AddCleanOp; applying its cleanup rules to every append would change behavior.

Public PopActivatablePanel exec `140810760` reads Panel then calls `1407e0c80`.
It also uses predicted membership to reject null/redundant requests. For an
accepted request it visits predicted stack from top down through the requested
Panel, submitting one Pop per Panel via AddCleanOp, each with its own GUID and
all three flags true. If a Panel remains immediately below the requested one,
append an Intro for that Panel directly with a fresh GUID/all flags true. If
`e0` is false, call BeginOperationProcessing.

AddCleanOp `1407a95e0` has two specific cleanup rules:

1. If the queue is nonempty, incoming Outro, last queued operation Intro, and
   incoming Panel is null or equals that last Intro's Panel: remove the last
   Intro **and return without appending the Outro**.
2. Otherwise if incoming Pop, **first** queued operation Intro, and its Panel
   equals the Pop's Panel: remove that first Intro, then append the Pop.

All other paths append the entire new record. In particular, the second rule
checks the first queued record, not the last one. Do not generalize this into
arbitrary cancellation or deduplication.

## Processing gates

SuspendStartingOperationProcessing exec `140811a20` sets manager byte `e0=true`;
ResumeStartingOperationProcessing `1408108f0` clears it then calls
BeginOperationProcessing. BeginOperationProcessing only starts when byte `fc`
is false and Operations is nonempty. It sets `fc=true`, uint32 `100=0`; if
byte `fd` was false, sets it true and broadcasts native bool multicast `90`;
then calls StartNextOperation `1407fc000` synchronously.

IsInputSuspended exec `140810290` returns `fd || fe`. These two flags are not
interchangeable with the enqueue-start gate `e0` or processing flag `fc`.
StartNextOperation's empty-queue path clears `fc` and uint32 `100`, but **does
not itself clear `fd` or broadcast resumed input**. The tick proof below binds
the subsequent three-invocation delay; do not invent an immediate empty-queue
unsuspend policy.

For a leading Pop run, StartNextOperation copies the entire contiguous Pop
prefix into a temporary array, increments `f8` for every copied record, removes
the entire prefix from Operations, then installs each Panel's pre/post Pop
callbacks and calls cleanup followed by OnBeginOutro. All counts and queue
removals occur **before** the first completion callback can run. Callback
OnPostPanelDeactivatedForPop decrements `f8`; only the transition to zero calls
StartNextOperation. The temporary batch survives synchronous callback reentry.
These details are required for both immediate native defaults and delayed
Blueprint transitions.

The Panel checkpoint proves all five callback bodies and exact native/dynamic
notification phases. The full non-Pop paths and completion behavior follow.
No shared Native/generated/Engine edits are authorized here.

Non-Pop processing first copies the front record to local storage and removes
it from Operations **before** executing any callback/Blueprint event. All
remaining references below use that local copy and captured identifier, so
reentrant appends/removals cannot invalidate the active record.

| Operation | Exact processor behavior after consuming its record |
| --- | --- |
| Intro | Search the current stack for this Panel. Only when found and inactive, bind pre/post activation callbacks (`3d0`/`3e0`) with GUID, assign Panel's weak manager `3b0`. If IsIntroed byte `303` is false, set it true and invoke OnBeginIntro; otherwise set bIsActive true and invoke activation virtual `488` directly |
| Outro | If record.Panel is nonnull, return without advancing. If the stack is empty, recurse into StartNextOperation immediately. Otherwise use the current top Panel, bind post-deactivation-for-push callback (`400`) with GUID. If bOutroPanelBelow is false, clear bIsActive and invoke deactivation virtual `490` directly; otherwise call held-action cleanup and OnBeginOutro |
| Push | Add Panel only if absent from current stack. On insertion, if Panel byte `304` is not true, set it true, call virtual `4e8`, then OnAddedToActivationStack wrapper `1408090b0`. Broadcast manager native no-argument multicast `48` even if the Panel was already present. If bActivatePanel is false, recurse into StartNextOperation immediately. Otherwise bind pre/post activation callbacks, assign weak manager `3b0`, then if bIntroPanel is true set `303` and invoke OnBeginIntro; if false set bIsActive and invoke `488` directly |
| Invalid/other | Return after consuming the record, without advancing |

Intro when Panel is absent or already active also returns without advancing.
These are real original return paths, not an instruction to silently skip
unexpected records. The normal enqueue contracts constrain reachable records;
adding a recovery loop would be a behavior change. A direct activation does
**not** set IsIntroed, and direct deactivation does **not** clear it. This is why
re-introducing a lower Panel can bypass its intro transition after a direct
deactivation, while a completed outro clears `303` through EndOutro.

For batch Pop, neither bIntroPanel nor bActivatePanel nor bOutroPanelBelow
controls dispatch: each snapshotted Panel gets pre/post Pop callbacks, cleanup,
and OnBeginOutro. All prefix records/counts are prepared before invoking the
first event. The original can complete native defaults synchronously or wait
for Blueprint EndOutro calls in any order; each post-Pop callback decrements
the already established count and only the last starts the next queued record.

The callbacks are normal weak UObject delegates carrying the operation GUID.
Their bodies unbind themselves, broadcast stack/activation changes, and directly
call StartNextOperation where proven in the Panel map. Preserve synchronous
reentry: do not defer all completions to a tick or process the queue with an
unconditional while-loop. In particular, the manager pre-activation callback
can mutate the stack before base/panel activation notifications run.

### Suspension ends after three eligible tick calls

Manager C++ constructor `140796de0` calls registration constructor `144617dd0`
with `this+28`, then installs secondary vtable `1459ed5f8` there. Slot 0 is
`1407ffc50`, the tick body; its accesses are relative to **this+28**, not the
UObject base. Thus tick `d4/d5/c8/d8/68` are manager `fc/fd/f0/100/90`.
The original registration constructor adds this secondary object to the engine
tickable registry, and its slot-8 getter `1407c5600` returns tick type 2 for CDOs
and 1 otherwise, using the UObject flag at adjusted-this minus `20`.
The current Engine's `Tickable.h` supports the interface names/layout (Tick at
slot 0, GetTickableTickType at 8, Always=1/Never=2); the original stores and code
are the behavior evidence.

The tick body is exactly:

```text
if operation_suspended(fd):
    if !processing(fc) and Operations.Num == 0:
        ++idle_tick_count(100)
        if idle_tick_count > 2:
            operation_suspended = false
            broadcast native bool delegate 90(false)
else if CurrentlyHeldActionInputHandler's object and interface words are both nonnull:
    call interface virtual +28 (original float argument register XMM1 is untouched)
```

There is no held-action tick on the invocation that clears suspension; it
returns after the broadcast. While processing or records remain, the idle
counter is left unchanged. BeginOperationProcessing and empty-queue completion
reset it to zero. External suspension byte `fe` does not gate this tick body:
`fd` can clear and broadcast false while public IsInputSuspended remains true
because of `fe`. Never replace the source bool broadcast with a combined-state
edge notification.

The slot-18 profiling function did not decompile reliably and is not used to
infer behavior. Batch 6 also contains a deliberately rejected interior-fragment
probe at `1408022d0`; it is not a valid complete-function proof. The complete
tick proof is `1407ffc50` plus constructor/vtable/register evidence in batches
8, 10 and 11. All transient Ghidra function creation rolled back.

## Manager creation is controlled by legacy-input selection

The source lifecycle matters before wiring the queue into RootLayout.
Original CommonUISubsystem primary vtable `145a0c7d0` has the standard
ShouldCreate/Initialize/Deinitialize slots at `260/268/270`:
`1407fb210`, `1407ce490`, `1407b8610`. Initialize resets four global counters;
it does **not** construct CommonInputManager. Deinitialize removes subsystem
bindings from manager multicast `90` and marks the manager for GC. The current
USubsystem header is contextual support for these names, not a replacement for
the original constructor/table evidence.

Actual enable/disable helper `1407f7b90(subsystem,enabled)`:

1. If no manager and enabled: NewObject CommonInputManager with subsystem Outer;
   assign subsystem `50`. Write weak subsystem to manager `d0`; obtain input
   subsystem through `14460bc60` → `144214d90` → `14081b480`, write weak input
   subsystem to manager `d8` and GlobalInputHandler `60`. Bind weak subsystem
   callback `1407c9550` to manager native bool multicast `90`; broadcast native
   subsystem bool multicast `58(true)`.
2. If manager exists and disabled: remove bindings owned by subsystem from
   manager `90`, mark the manager for GC, clear subsystem `50`, broadcast
   subsystem native bool multicast `58(false)`.
3. Other combinations return without these effects.

Manager PostInitProperties override `1407e1ed0` (primary slot `40`) calls its
super, creates CommonGlobalInputHandler with manager Outer, stores it at `c8`.
The suspension callback `1407c9550` broadcasts subsystem's reflected
OnInputSuspensionChanged at `30` with the original Bool. This completes the
native `90` → subsystem dynamic notification path.

The enable caller `14515a790` obtains CommonUISubsystem from its Outer's game
instance and passes its own byte `50`. **This is exactly
UFortUIManager.bUseLegacyInputSystem**: original class block `14700e250` names
Bool setter `14075d4a0`, whose bytes write 1 to `RCX+50`.
UFortUIManager native constructor `145143bd0` explicitly initializes it false.
Startup constructor callback `145312900` calls `145312b50` → that base constructor,
then installs primary vtable `147011440`; its slot `268` is `14515aac0`, which
calls `14515a790` before setting the FortUIManagerInterface pair at `110/118`.
The intervening constructors do not set `50` true. The earlier reflection
index's Startup candidate `147011088` is the constructor-installed parent
table, not the final Startup table.

This proves a **native constructor default**, not the value of any loaded
Blueprint-derived manager or a live selected policy. A source override can
change it. Do not force-enable the legacy manager or allocate it unconditionally
in Initialize merely to get an activation path. Original nonlegacy action
bindings also exist (Panel container `310`, already observed separately), so
legacy queue reconstruction alone cannot claim full input parity.

## Implementation boundary after this checkpoint

The record, predicted-stack algorithm, enqueue cleanup, full queue dispatcher,
captured weak/GUID callbacks, direct versus transitioned activation, pop batch
counts, three-tick suspension tail and source enable gate are implementation-ready
as a reviewed translation. Existing typed reflected members can be used; native
private fields/delegates and GUID must be added from this evidence, without
fabricating reflected parameter names or reusing the new input binding path.

Before claiming a faithful integrated manager, preserve the actual selected
UI-manager policy and implement lifecycle/held-action dependencies rather than
stubbing them. The nonlegacy binding path and full global-input handler dispatch
are separate unfinished work. No native implementation, UE build, stage write,
actual widget activation or milestone credit is claimed.

Reset helper `1407ae2c0` first iterates the stack top-down: if Panel `304` is
true, clear it, call OnRemovedFromActivationStack, then virtual `4f0`. It then
iterates the stack in its stored order and calls Panel reset `1407f1b20` on
each, before clearing stack/queue/counts, flags `fc/fd/fe` and counter `100`.
It does not broadcast manager `90(false)` during this reset.

Panel reset `1407f1b20` has the exact following order:

1. Clear bIsActive `288` and IsIntroed `303`, then held-action cleanup
   `1407ae640` (including float progress-zero when its guards match).
2. Unbind/free private pre-activation callback `3d0`.
3. Clear dynamic Panel OnWidgetActivated `2e0`, then base
   BP_OnWidgetActivated `268`.
4. Unbind/free private post-activation `3e0`, then pre-deactivation `3f0`.
5. Clear dynamic Panel OnWidgetDeactivated `2f0`, then base
   BP_OnWidgetDeactivated `278`.
6. Unbind/free private post-deactivation callback `400`.

It invokes neither activation/deactivation virtuals nor the completion hooks.
It does not clear native base multicast `290/2a8`, Panel weak manager `3b0`,
or remove the input-type subscription stored at `3b8` in this body. Calling
EndOutro or DeactivateWidget as a replacement would introduce notifications and
input subscription effects absent from this original reset path.
