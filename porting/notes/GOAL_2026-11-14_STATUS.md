### Glider early deploy: static findings (2026-11-15, no client run)

- The pawn's per-tick glider logic is client code (0x142354c98, continued at 0x14235515b): it sets `bIsParachuteForcedOpen` (pawn+0x10e7 bit 1) when the pawn Z is within `AFortGameStateAthena::DefaultParachuteDeployTraceForGroundDistance` (GameState+0x20b4) of the ground Z returned by a pawn-virtual trace (slot 0x12e8 -> owner->0x148). Deploy requests come from the jump input via `CheckJumpInput`. `bIsParachuteOpen`/`bIsParachuteForcedOpen` replicate COND_SimulatedOnly, so the owning client is not driven by the server for either.
- The only server-controlled input is the game-data distance: the log shows `deployGroundDistance=10000.0` straight from `AthenaGameData` row `Default.Parachute.DeployTraceForGroundDistance` (retail value, nothing overrides it). The skydive re-kick that flipped `bIsSkydiving` 0.75 s after exit is opt-in only. The server never writes the glider flags except resetting `bIsParachuteOpen=false` at skydive start/landing.
- Conclusion: an early auto-deploy is not caused by a server write. Remaining suspects are client-local: the ground trace (slot 0x12e8) hitting stand-in collision high above the drop, or a jump press landing in the 0.6 s MOVE_Falling window before `bIsSkydiving` is set (the delay is tunable with `-FortniteSkydiveBeginDelay=`). Needs a client run to separate them; not run per the user's "no client runs".
