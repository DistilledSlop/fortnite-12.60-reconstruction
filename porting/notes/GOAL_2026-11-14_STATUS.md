## Findings from the 2026-11-14 23:15 client test (server log FortniteLinux.log)

- Log spam: `run_chrono_server.sh` ran with `LogNetPlayerMovement VeryVerbose` and `-FortniteProbeMovementDefaults` (p.NetShowCorrections=1, per-second SprintProbe, air-curve dumps). Both are now opt-in (FN_SERVER_LOG_CMDS / FN_SERVER_ARGS).
- Cosmetics were never applied: `Cosmetics: Glider ... not loadable` for every glider, backpack, contrail, wrap and dance, because the server stage only held a handful of definitions. All 1880 definitions under Athena/Items/Cosmetics (Gliders, Backpacks, Pickaxes, Dances, Contrails, ItemWraps, MusicPacks, 12 MB) are now staged with `tools/stage_server_content.py` (stage is git-ignored; rerun the same command on a fresh stage).
- Skydive stutter / stuck glider: about 1760 corrections in 85 s of skydive (server has no skydive physics that matches the client). Road jitter: 2-4 unit corrections with `Base: S_Sidewalk...` (server collision differs from the client). Server authority stays the default for everything. Stopgap: while skydiving/gliding the server takes the client position and mode (`bServerAcceptClientAuthoritativePosition`), restored on landing. `-FortniteServerSkydiveAuthority` disables the stopgap; `-FortniteClientMovementAuthority` takes client movement for everything (comparison runs). Launcher: `FN_SERVER_EXTRA_ARGS="-FortniteClientMovementAuthority" bash porting/run_chrono_server.sh`.
- Harvest circles stopping / broken objects lingering then popping: after an object reached 0 health the server kept it for a guessed 5 s (`SetLifeSpan`), swings kept landing on it (`applied=0`, no new weak spots) until it popped. Fallback is now 1 s (`-FortniteDeathLifespan=<s>` to tune); applies to harvestables and player-built pieces. Not client-tested; the original constructor default of `LifespanAfterDeath` is still unrecovered.

Correction breakdown of the 23:15 run (3879 FortMovementPair rows, user log archived in /mnt/vibrato/archive-from-root/user-test-logs/): 1757 of the large corrections were in the skydive/glider modes (client/server mode 19/19: 1526; client 20 vs server 19: 231, i.e. the client switched to the glider mode while the server stayed in skydive, which is the stuck-glider symptom). Ground movement was close to in sync (median error 0.016 uu over 599 sprint moves); only about 130 ground corrections in the whole run: one 70 uu spike at sprint start and a series of 2-4 uu errors along the direction of travel on `S_Sidewalk_1x1_A_NoCurb` (probable physical-material/friction difference on that mesh; not changed). The skydive stopgap (client position and mode accepted until landing) targets the 1757.


## Findings from the 2026-11-15 04:25 client test (run with `-FortniteClientMovementAuthority`)

- Chests: the client's `ServerAttemptInteract` reached the handler (`LootSearch: attempt container=Tiered_Chest_Athena11_2 ... rejected reason=interact_disabled`). The server-side `bAllowInteract` bit is 0 on the placed chests although `OriginalDefaults.json` sets it on BuildingSMActor, no level or Blueprint clears it, and it is not replicated. The check is now logged once and ignored for containers and for the Blueprint-interact branch (porta-potty/dumpster); `bAlreadySearched`/`bDestroyed`/distance still gate. Not client-tested.
- Fall damage: the `AthenaFallingDamage` `Player` row is keyed by fall DISTANCE (cm; 1300 -> 10 %, 2304 -> 100 %), not speed. Player gravity here is about 2500 cm/s^2, so the old speed lookup gave 12 damage for a 3.9 m drop and 100 for a 13.9 m drop. `FortAthenaFallDamage.cpp` now evaluates the curve at the drop. The hit cue is still not sent for environmental damage (gameplay-cue serialisation is stubbed), so the client only sees the health bar change. Not client-tested.
- Skydive contrail: the skydive "re-kick" (`bIsSkydiving` off/on 0.75 s after the bus exit) restarted the client's skydive and ended the contrail about a second in. It is now opt-in (`-FortniteSkydiveRekick`). If steering fails again until the glider is deployed, that flag is the knob to retry. Not client-tested.
- Road glitch with client authority: the flag was on the command line, and the whole 04.25-04.33 run produced only 3 movement corrections (`ClientAdjustPosition` x1, `ClientVeryShortAdjustPosition` x2, all at world time 343 s). So the road glitch is not server position correction; it is something client-side or visual (movement base, smoothing, or physical material). Needs a description or a clip of what it looks like.
- Weak spots: placement now uses the camera ray (400 uu) like the original `SpawnWeakSpot`. Built, not client-tested.
- Dances/backpacks "not loadable": the backend sends lower-case template ids (`eid_celebration`), the staged files are `EID_Celebration.uasset` and the stage asset registry lists almost nothing, so the plain-path fallback misses on case-sensitive Linux. Fix: scan the staged folder for the real file name.
